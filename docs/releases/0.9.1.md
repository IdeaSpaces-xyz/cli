# CLI 0.9.1 — launch from any post, with the Thread's frame

You can now prepare a session from any local Thread post, not only a post carrying a Map. The launch uses the Thread's newest snapshot that carries a Map, or its opening post's Map, rather than the chosen post's Map. It includes the Thread's Agreement and a record of posts since that Map, so a new session can see where the work stands.

The Note still comes from a pinned post in that Map. Use `--member <ordinal>` to choose it, or inspect the reported choice: the CLI looks for a matching post and otherwise uses the Map's first Thread post. It refuses with guidance if there is no usable Map/Note. The starting post and the chosen Note are reported separately; do not assume they are the same.

Large launch Maps now have another way to fit: after reading members at lower depths, the shared launch reader can leave members out, last first. `threads launch-text` reports what was lowered or omitted and where to read it. If needed, its Thread frame lists fewer later posts and finally gives the Thread Agreement as a pointer; the selected agent's Agreement and the Note stay whole. If those cannot fit, it still refuses with guidance. This changes the 0.9.0 launch-budget behavior, which lowered Map depths but did not drop members.

This fixes `threads launch-text` after 0.9.0. It still only reads: it does not launch a model, post a reply, acknowledge unread work or grant access. Its JSON adds the launch Thread, the source Map post and omission details; it is the app engine's for now. Do not build a stable integration on `lowered` or `cut` yet.

## Coming from 0.8.2 or earlier

These changes first shipped in **0.9.0** and are included here:

- **Work with hosted Spaces.** List them with `spaces list --hosted`, open a Space, create one in a Vault, add or remove members, and export or import a copy. A Space is a named Map, not a Repo. Local and hosted Spaces remain independent; copying does not set up sync or give anyone access.
- **Place a hosted Thread in a Space.** `threads new --hosted` and `threads send` accept `--home map:<id>`. Placement alone adds no Map member and grants no access. Local Threads do not take `--home`.
- **Edit deliberately.** Hosted Space edits are owner-only. Read the Space first, review the change and use its current head with `--if-match`. A retry after an uncertain answer keeps the same command id and the exact same arguments. Removing a member previews until `--yes`.
- **Know where local posts are.** Thread reads distinguish local-only, committed, pushed and unknown posts. Local author names are claims, not verified identities. `threads check` finds posts changed after their first commit.
- **Use Windows paths and installed runtimes reliably.** Alternate spellings and junctions for the same local folder match. npm-installed Claude and Pi `.cmd` launchers are discovered through PATH or an explicit path, without evaluating batch text or turning prompts into shell commands. Pi's version is read even when it is printed on stderr.

If a script reads `spaces list --hosted --json` or `spaces open --json`, those commands return Maps rather than the old coordination objects. Plain `spaces list` keeps the legacy list. Local Thread JSON adds post-location information; text readers will also see `claimed by` before local author names. See the [0.9.0 notes](0.9.0.md) for the earlier transition; the launch-budget change above supersedes its no-dropped-members description.

## Installing

```sh
npm install -g @ideaspaces/cli@0.9.1
```

The CLI needs Node 20 or newer. The Claude plugin, Pi package and Desktop carry their own CLI pins; installing this npm release does not update those consumers. Their release or pin change is separate.

Windows CI and package checks are not a claim that production browser OAuth or an authenticated Claude/Pi model turn was tested. No new native MCP Spaces tool is part of this release.
